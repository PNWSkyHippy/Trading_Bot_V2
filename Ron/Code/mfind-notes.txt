mfind: nice progress. Here are some pointers in words for what’s left:

Running a command on the files found (one at a time vs batch): keep every match in a list first. One-at-a-time mode runs the command once per path.

 Batch mode runs it once with all the paths added on the end. Pass the paths as a list of arguments, not one string, so spaces in names don’t break it.
S
ort by byte count: once results are in a list, sort it using each file’s size as the key, with a flag for big-to-small.

Filter by extension: compare the end of the name, lowercased, against a set of extensions, so .JPG and .jpg both match.

Filter by file type: the file/dir/link checks you already use for hidden files work here too.

Recent (newest first, any depth): walk the whole tree into one flat list, then sort by access time from the file’s stat info, newest at the top. 
On a Mac, access time can be stale depending on disk settings, so you may want a modified-time option too.

Python	JS

{k: v for k, v in pairs}	Object.fromEntries(pairs)
sum(nums)	nums.reduce((a, b) => a + b, 0)

It reads left to right, as a pipeline, which should suit your Unix filter instincts: filter is like grep and map is like sed.

Right call — and worth saying out loud: executable and empty aren’t file types, they’re separate tests. find treats them as their own primaries 
(-type, -executable, -empty) rather than values of -type, and you’ll want the same split: the type enum stays the 7 S_IS* cases, and executable/empty are 
independent switches layered into the same per-entry filter pass.

Empty — two different checks depending on what the entry is:

regular file → statinfo.st_size == 0 (you already have the stat, so it’s free).
directory → size is meaningless (a dir’s st_size isn’t 0 when empty on most filesystems). You have to look inside: “no entries,” e.g. nothing yielded by 
os.scandir(path) / an empty os.listdir(path). That’s an extra syscall, so only do it when the empty switch is actually on.
find -empty = empty regular file or empty directory, so if you want parity, cover both.

Executable — a permission question, two ways to read it:

os.access(path, os.X_OK) — matches find -executable: “can the current user execute/traverse this,” honoring your uid/gid. This is the one that behaves right 
on directories too (exec bit on a dir = searchable).
raw bits — statinfo.st_mode & (stat.S_IXUSR | stat.S_IXGRP | stat.S_IXOTH) if you want “any execute bit set” regardless of who you are. Also free since you have 
the mode.

The one caveat you can’t dodge: on Windows os.access(path, os.X_OK) is nearly meaningless — it tends to return True broadly, because Windows executability is 
really “extension is in PATHEXT” (.exe/.bat/.cmd/...), not a mode bit. So if the exec filter needs to be sane on Windows, that’s a platform branch (check the 
suffix against PATHEXT) rather than the stat bits. Same spirit as the st_type lesson — the
 stat-bit view is Unix-shaped.
