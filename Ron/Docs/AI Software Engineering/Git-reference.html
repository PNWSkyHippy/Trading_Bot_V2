👋 Basics — Git, GitHub & Version Control

Git   GitHub   version control  # what you are actually using
Git is a free, open-source distributed version control system. Created by Linus Torvalds in 2005; maintained by Junio Hamano ever since
It tracks what changed, who changed it, when, and why — and lets you go back to any earlier state
Over 70% of developers use Git. Every commit is stored locally, so you can work offline and still have the full history
GitHub is a hosting service for Git repositories (owned by Microsoft since 2018). GitLab and Bitbucket are alternatives
Git ≠ GitHub: Git is the tool on your machine; GitHub is a website that stores a copy of your Git repository

🔄 The Daily Workflow — Files, Staging & Commits

working directory   staging area   repository  # the three areas
Working directory — your actual files on disk. Edit them freely; Git does not record anything yet
Staging area (index) — the waiting room. You choose exactly which changes go into the next commit
Local repository — the permanent history inside .git. A commit moves staged changes here
[Working Directory] --git add--> [Staging Area] --git commit--> [Repository]
        ^                                                             |
        |______________________ git checkout / restore _______________|
Why stage? It lets you commit some changes while leaving others for later — small, focused commits

⏪ Undo, Reset & Recovery — Fixing Mistakes

which undo command?  # pick the right tool before you type
GoalCommandRewrites history?Safe on shared branch?
Discard edits in a filegit restore <file>noyes (local only)
Unstage a filegit restore --staged <file>noyes
Undo last commit, keep changesgit reset --soft HEAD~1yesno
Undo last commit, unstage changesgit reset HEAD~1yesno
Undo last commit and discard changesgit reset --hard HEAD~1yesno
Undo a pushed commitgit revert <commit>no (adds a commit)yes
Fix the last commit message/filesgit commit --amendyesonly if not pushed
Recover a lost commit/branchgit reflog + reset/branchdependslocal
Golden rule: reset/amend/rebase rewrite history; revert adds new history. On a shared branch, prefer revert
git restore  # discard local edits or unstage (Git 2.23+) 
git restore index.html              # discard unstaged edits (NO UNDO)
git restore .                       # discard every unstaged edit
git restore --staged index.html     # unstage, keep the edits
git restore --source=HEAD~1 index.html   # bring back the previous version
git restore --source=v1.0 .         # restore a whole old snapshot
git restore replaced the confusing git checkout -- <file> for files (checkout still works)
Restoring from the working tree is permanent — uncommitted edits are not in Git, so the reflog cannot save them
git reset  --soft  --mixed  --hard  # move the branch pointer 
git reset --soft HEAD~1     # undo commit, keep changes STAGED
git reset HEAD~1            # undo commit, keep changes UNSTAGED (default --mixed)
git reset --hard HEAD~1     # undo commit and DELETE the changes
git reset --hard 9a9add8    # jump back to a specific commit

git reset HEAD index.html   # unstage one file (older syntax)
git reset -- file.txt       # unstage one path
ModeHEAD / branchStaging areaWorking files
--softmoveskept (staged)untouched
--mixed (default)movesreset (unstaged)untouched
--hardmovesresetdiscarded
Find the target first with git log --oneline; HEAD~1 is one commit back, HEAD~3 three back
ORIG_HEAD remembers the pre-reset position: git reset --hard ORIG_HEAD undoes a reset
--hard permanently deletes uncommitted work. Committed work can still be recovered with git reflog
Never git reset a branch that other people already pulled — use git revert instead
git revert  # undo a commit by adding its inverse (safe for shared branches) 
git revert HEAD                # revert the latest commit
git revert 52418f7             # revert a specific commit
git revert HEAD~2              # revert the third commit back
git revert --no-edit HEAD      # accept the default message
git revert HEAD~3..HEAD        # revert a range
git revert --abort             # cancel a conflicted revert
git revert --continue          # after resolving conflicts
Revert creates a new commit that reverses the old change — history stays intact, so it is safe after pushing
Reverting a merge commit needs a parent: git revert -m 1 <merge-hash> (1 = first parent, usually main)
Reverting does not erase the original commit; the change is still in history, just cancelled going forward
git commit --amend  # fix the most recent commit 
git commit --amend -m "Corrected commit message"
git add forgotten.txt
git commit --amend --no-edit          # add the file, keep the message
git reset HEAD^ -- unwanted.txt       # remove a file from the last commit
git commit --amend                    # then save
Amend replaces the last commit — it gets a new hash. The old commit remains in the reflog for a while
Typical uses: typo in the message, forgot a file, accidentally included a file, want to add a sign-off
If the commit was already pushed, amending requires a force push that rewrites public history — coordinate with your team
Do not amend a commit that is not yours (for example, on main) — amend only your own unpushed work
git reflog  # the safety net: where HEAD has been 
git reflog
# e56ba1f (HEAD -> main) HEAD@{0}: commit: Revert "Just a regular update..."
# 52418f7 HEAD@{1}: commit: Just a regular update, definitely no accidents
# 9a9add8 (origin/main) HEAD@{2}: commit: Added .gitignore
# 81912ba HEAD@{3}: commit: Corrected spelling error

git reset --hard HEAD@{2}        # jump back to that point
git checkout -b rescue 52418f7   # recreate a branch at a lost commit
The reflog records commits, resets, merges, checkouts and rebases — even commits no branch points to anymore
Entries are local and expire (default 90 days for reachable, 30 for unreachable). It is not pushed to remotes
git reflog expire --expire=30.days refs/heads/main
git gc --prune=now
git reflog show main shows the reflog for one branch
The reflog cannot recover files that were never committed — commit early if the work matters
recovery recipes  # deleted branch, deleted file, bad hard reset
Deleted a branch:
git reflog
git checkout -b recovered-branch <commit-hash>
Deleted or overwrote a file (already committed):
git restore filename.txt
git restore --source=HEAD~2 filename.txt   # from an older commit
Hard reset to the wrong place:
git reflog
git reset --hard HEAD@{2}
Bad rebase / merge:
git rebase --abort
git merge --abort
git reset --hard ORIG_HEAD
Recovery only works for work that reached Git (committed or stashed). Untracked files deleted outside Git are gone
git clean  # delete untracked files (permanent) 
git clean -n            # dry run: list what WOULD be deleted
git clean -f            # delete untracked files
git clean -fd           # also delete untracked folders
git clean -fdx          # also delete ignored files (build output, .env!)
Useful after a build leaves junk, or when switching to a clean state
git clean -fdx can delete .env, databases and local configs — always run -n first

🌿 Branching — Parallel Universes for Your Code

what is a branch?  # a movable pointer to a line of commits
A branch is a separate workspace where you can try ideas without affecting main. It is just a pointer to a commit — cheap and fast
main (older repos: master) is the default branch. Keep it stable and deployable
Create a branch for every feature, bug fix and experiment. Merge it back when it is reviewed and tested
Without branches: copy files, lose track of versions, and merge by hand. With branches: one command switches context
main:     A --- B --- C ----------- M
                       \           /
feature:                D --- E ---
Branches are local until you push them. Creating 100 branches costs almost nothing
git branch  # create, list and inspect branches 
git branch                       # list local branches (* = current)
git branch -a                    # local + remote-tracking branches
git branch -r                    # remote-tracking only
git branch -v                    # last commit on each branch
git branch -vv                   # + upstream tracking info
git branch feature/login         # create (does NOT switch)
git branch --merged              # branches already merged into HEAD
git branch --no-merged           # branches not yet merged
Sample output — the * marks the branch you are on:
  feature/login
  bugfix/header-crash
* main
Remote-tracking branches look like remotes/origin/main; they are read-only snapshots of the remote
git branch name creates the branch but leaves you on the current one — switch to it next
git switch   git checkout  # change branches 
git switch feature/login         # modern (Git 2.23+)
git checkout feature/login       # classic, still works

git switch -c feature/login      # create + switch
git checkout -b feature/login    # create + switch (classic)

git switch -                    # back to the previous branch
git switch main                 # return to main
git checkout also restores files, which made it confusing. git switch only changes branches; git restore only touches files
Switch with uncommitted changes is allowed if the files do not differ between branches; otherwise commit or stash first
git checkout <commit-hash> detaches HEAD — see the detached HEAD entry below
working in a branch  # the emergency-fix example
You are editing hello-world-images when a bug appears on main. Do not mix the two:
git switch main
git switch -c emergency-fix
# fix the bug, then:
git add index.html
git commit -m "Fix header crash on the home page"
git switch main
git merge emergency-fix
git branch -d emergency-fix
Your unfinished feature branch stays exactly where you left it. Switch back with git switch hello-world-images
This is the whole point of branching: independent work, clean merges, no file-copy chaos
Commit or stash before switching — uncommitted changes follow you across branches and can cause surprises
rename a branch  # git branch -m 
git branch -m old-name new-name     # rename another branch
git branch -m new-name              # rename the current branch

git push origin --delete old-name   # if it was already pushed
git push -u origin new-name         # publish the new name
Renaming a pushed branch leaves the old name on the remote until you delete it
delete a branch  # -d is safe, -D is forceful 
git branch -d feature/login     # only if fully merged (safe)
git branch -D feature/login     # force delete, even if unmerged
git push origin --delete feature/login   # delete the remote branch
Git refuses -d on an unmerged branch so you do not lose commits — merge it, or use -D if you truly mean it
Deleted by accident? git reflog still has the commit; recreate with git branch recovered <hash>
Deleting a branch does not delete its commits immediately; unreachable commits are eventually garbage-collected
detached HEAD  # checkout a commit instead of a branch
git checkout 09f4acd moves HEAD to a commit, not a branch. New commits there belong to no branch
git switch --detach v1.0        # intentionally inspect an old version
git switch -c hotfix-v1         # keep work: create a branch HERE
git switch main                 # discard and go back
Detached HEAD is fine for looking around, building an old release, or testing — just branch before committing
Commits made in detached HEAD are only reachable through the reflog once you switch away — easy to lose
branch best practices  # names, size, lifetime
Descriptive names with a prefix: feature/login-form, bugfix/user-auth, hotfix/payments, chore/update-deps
One purpose per branch. A branch that does five things is impossible to review or revert
Keep branches short-lived. Merge or delete them; stale branches rot and conflict
Regularly merge main into your feature branch (or rebase onto it) to catch conflicts early
Never commit directly to main on a team project — use a branch and a pull request

🔀 Merging & Merge Conflicts

git merge  # bring another branch into the current one
Switch to the branch you want to merge into, then merge the other branch into it
git switch main
git merge emergency-fix
# Updating 09f4acd..dfa79db
# Fast-forward
#  index.html | 2 +-
#  1 file changed, 1 insertion(+), 1 deletion(-)
Fast-forward — the target branch has no new commits, so Git just moves the pointer forward. No merge commit
Three-way merge — both branches moved, so Git creates a merge commit with two parents
OptionEffect
git merge branchmerge branch into the current branch
--no-ffalways create a merge commit, even when fast-forward is possible
--squashcombine the branch's changes into one staged change (no merge commit yet)
--abortcancel a merge in progress
--continuefinish after resolving conflicts
-m "msg"set the merge commit message
Commit or stash before merging — a dirty working tree blocks the merge or mixes unrelated changes into it
--no-ff   --squash  # keep history, or collapse it 
git merge --no-ff feature-branch
# Merge made by the 'recursive' strategy.
#  index.html | 2 +-
#  1 file changed, 1 insertion(+), 1 deletion(-)

git merge --squash feature-branch
# Squash commit -- not updating HEAD
# Automatic merge went well; stopped before committing
git commit -m "Add the whole feature"
--no-ff preserves the branch shape in history — useful for feature branches where you want to see the merge point
--squash turns 20 messy "wip" commits into one clean commit on main — the feature branch history is not linked
After --squash, Git does not know the branch was merged; do not merge it again or you will get duplicate changes
merge conflict  # two branches changed the same lines
Git merges automatically when changes are in different places. A conflict happens when both branches changed the same part of a file
Git pauses the merge, marks the file, and waits for you to choose the final content
git merge hello-world-images
# Auto-merging index.html
# CONFLICT (content): Merge conflict in index.html
# Automatic merge failed; fix conflicts and then commit the result.

git status
# Unmerged paths:
#   both modified: index.html
This is normal, not a disaster. The conflict only exists until you edit the file and stage it
resolve a conflict  # edit, stage, commit
1. Open each conflicted file. Git inserted markers:
<<<<<<< HEAD
<p>This line is here to show how merging works.</p>
=======
<p>A new line in our file!</p>
<div><img src="img_hello_git.jpg" alt="Hello Git"></div>
>>>>>>> hello-world-images
2. Replace the whole block with the version you want — keep yours, theirs, a mix, or something new. Delete all three marker lines
3. Stage the resolved file and finish:
git add index.html
git status                    # All conflicts fixed but you are still merging
git commit                    # concludes the merge (message is pre-filled)
# or: git merge --continue
Cancel instead: git merge --abort puts everything back the way it was before the merge
Leaving a marker line (<<<<<<<, =======, >>>>>>>) in the file is the classic broken-merge bug — search for it before committing
mergetool   --ours   --theirs  # resolve visually or pick a side 
git mergetool                         # opens your configured 3-way merge tool
git checkout --ours index.html        # keep the current branch version
git checkout --theirs index.html      # keep the incoming branch version
git add index.html
Configure a tool once: git config --global merge.tool vscode (or meld, kdiff3, vimdiff)
--ours / --theirs take the whole file from one side — they do not merge individual lines

🔧 Rewriting History — Rebase, Cherry-pick, Patch & Stash

rebase vs merge  # two ways to combine branches
Merge keeps history as it happened and adds a merge commit. Rebase replays your commits onto a new base, producing a straight line
# merge: history shows the branch existed
main:     A --- B --------- M
               \           /
feature:        C --- D ---

# rebase: commits are copied, history looks linear
main:     A --- B --- C' --- D'
MergeRebase
Historytrue, with branches visiblelinear, rewritten
Commitsunchangednew SHAs (copies)
Conflictsresolved oncemay repeat per commit
Safe on shared branchesyesno
Best forintegrating finished workcleaning up local work before sharing
Golden rule of rebase: never rebase commits that exist outside your machine. Rewriting public history forces everyone else to repair their clone
git rebase  # move your branch onto a new base 
git switch feature
git rebase main                 # replay feature commits on top of main
git rebase main feature         # same, without switching first
git rebase --onto main old-base feature   # transplant a range
git rebase -i HEAD~3            # interactive: edit the last 3 commits
git rebase --continue           # after resolving a conflict
git rebase --skip               # drop the conflicting commit
git rebase --abort              # restore the pre-rebase state
Rebase is also the clean way to pull when your branch has local commits:
git pull --rebase origin main
# equivalent to: git fetch origin && git rebase origin/main
Set it as the default so git pull never creates accidental merge commits:
git config --global pull.rebase true
After a successful rebase, pushing needs --force-with-lease (safer than --force — it refuses if someone else pushed in the meantime)
git push --force-with-lease origin feature
A rebase conflict can appear once per replayed commit. Resolve, git add, then --continue — do not commit manually in the middle

git cherry-pick  # copy one commit onto the current branch
Use when you want a single fix from another branch without merging the whole thing
git switch main

git cherry-pick abc1234 def5678    # several commits
git cherry-pick abc1234..def5678   # a range (exclusive of the first)
git cherry-pick -x abc1234         # append "(cherry picked from ...)" to the message
git cherry-pick -n abc1234         # apply changes but do not commit
git cherry-pick --continue         # after resolving a conflict
git cherry-pick --abort
The result is a new commit with a new SHA — same diff, different identity
Typical use: backport a hotfix from main to a release/1.x branch

A patch is a text file containing a diff. Useful across repos, over email, or when the other side has no network access

git stash  # park unfinished work without committing
Stash saves your modified tracked files and restores the working tree to HEAD. Perfect for "I need to switch branches right now"
git stash                          # save tracked changes
git stash push -m "wip login form" # with a label
git stash -u                       # include untracked files
git stash -a                       # include ignored files too
git stash -p                       # choose hunks interactively

git stash drop stash@{1}           # delete one
git stash clear                    # delete all (irreversible)
Stashes are local only — they are not pushed and not shared

git stash branch feature/login stash@{0}
Conflicts on pop leave the stash in place — resolve, git add, then git stash drop
Stashes are easy to forget. Run git stash list periodically; a month-old stash is usually stale and better deleted

.gitattributes  # per-path behaviour: line endings, diffs, merges
.gitattributes tells Git how to treat certain files — it is committed and shared, unlike .git/config

Git LFS  # large files without bloating history
Git stores every version of every file. A 200 MB video committed ten times adds 2 GB to the repo forever
Large File Storage replaces the file content with a small pointer and keeps the bytes on a separate server
git lfs install

git lfs track "*.mp4"
git add .gitattributes
git add design.psd
git commit -m "Add design source via LFS"
git push

git lfs pull
Track patterns go into .gitattributes — commit that file so the whole team inherits the rules
GitHub gives 1 GB of free LFS storage and 1 GB/month bandwidth; beyond that it is billed
LFS must be set up before the first commit of the large file. Migrating later requires git lfs migrate import and a full history rewrite

submodules  # one repo nested inside another
A submodule pins another repository at a specific commit. Useful for shared libraries or vendored dependencies
git submodule add https://github.com/user/lib.git libs/lib
git commit -m "Add lib as submodule"

git submodule status
git submodule update --init --recursive
git clone --recurse-submodules https://github.com/user/project.git

# later: move the pin to a newer commit
cd libs/lib
git pull origin main
cd ../..
git add libs/lib
git commit -m "Bump lib to latest"
CommandDoes

git submodule update --remotemove to the remote's latest (then commit the new pin)
git submodule syncre-copy URLs from .gitmodules into config
git submodule deinit -f libs/libunregister a submodule
A submodule appears in git status as a single entry pointing at a commit — not as loose files
Submodules are the most common source of "works on my machine". For simple shared code, a package manager or a monorepo is usually less painful
worktrees  # several branches checked out at once
A linked worktree is a second folder sharing the same repository — no re-clone, no stashing to switch context
git worktree add ../project-hotfix hotfix/1.0.1
git worktree add -b feature/new-api ../project-api main
git worktree list
git worktree remove ../project-hotfix
git worktree prune
Each worktree has its own working tree and index but shares .git objects and refs
Perfect for: reviewing a PR while your main folder stays dirty, running a long build on one branch, comparing behaviour side by side
The same branch cannot be checked out in two worktrees at once — Git refuses to avoid index corruption
git bisect  # binary search for the commit that broke it
Instead of reading 500 commits, mark a good and a bad point and let Git halve the range each time — about 9 tests for 500 commits
git bisect start
git bisect bad                 # current commit is broken
git bisect good v1.2.0         # this tag was fine

# Git checks out a middle commit - test it, then:
git bisect good                # or: git bisect bad
# repeat until: "abc1234 is the first bad commit"

git bisect reset               # back to where you started
Automate it with a script that exits 0 for good and 1 for bad:
git bisect run npm test
git bisect run python -m pytest tests/test_login.py -q
git bisect log records the session; git bisect replay file reproduces it
Your working tree must be clean before starting. Uncommitted changes confuse every checkout bisect performs
signing commits & tags  # prove who wrote it
A GPG (or SSH) signature proves the commit came from the holder of the private key. GitHub shows a Verified badge
# list keys
gpg --list-secret-keys --keyid-format=long

# tell Git which key to use
git config --global user.signingkey ABCDEF1234567890
git config --global commit.gpgsign true
git config --global tag.gpgsign true

# sign one commit / tag
git commit -S -m "Signed commit"
git tag -s v1.0.0 -m "Signed release"

# verify
git log --show-signature -1
git tag -v v1.0.0
SSH signing (Git 2.34+) avoids GPG entirely:
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
Add the public key to GitHub as a Signing key (separate from an authentication key)
Signing proves the key holder made the commit — not that the code is good, nor that the author identity in the message is honest

⚠️ Git Traps & Gotchas

classic mistakes  # check this list before you panic
git reset --hard discards uncommitted work permanently — no confirmation, no undo
git clean -fd deletes untracked files and folders — including the ones you forgot to add
git push --force on a shared branch erases other people's commits; use --force-with-lease, and only on your own branch
Rebasing a branch others have pulled forces everyone to repair their clone
.gitignore does nothing for files already tracked — use git rm --cached
Deleting a file in a new commit does not remove it from history — the blob is still there and still cloneable
Committing a secret then deleting it is not enough — rotate the credential immediately
Committing node_modules, venv or build output bloats the repo forever
A merge conflict is not an error — stopping and asking is correct; deleting the markers without choosing is not
Leaving <<<<<<< / ======= / >>>>>>> markers in a file breaks the build silently
Detached HEAD: commits made there are not on any branch and vanish from view when you switch
git checkout . throws away every unstaged change in the repo — no prompt
git commit -am skips new files entirely (it only stages tracked ones)
Amending a commit that is already pushed requires a force-push — see the rebase rule
Line-ending mismatches make every line look changed; fix with .gitattributes + --renormalize
File-name case changes on Windows/macOS may be ignored by Git — rename via a temp name
Empty folders are not tracked — Git stores files, not directories (add a .gitkeep)
git pull with local changes can fail or create a surprise merge commit; commit or stash first
"Already up to date" but the file looks old — you may be on a different branch than you think; check git status
Two repos with unrelated histories refuse to merge without --allow-unrelated-histories
A shallow clone (--depth) breaks git log, blame and describe beyond the cut-off
Submodules are pinned to a commit — a plain git pull does not update them; use --recurse-submodules
Hooks are local and skippable with --no-verify; never rely on them for security
Git is not a backup: a force-push to the only remote can destroy history everywhere. Mirror or tag releases
On Windows, "dubious ownership" blocks Git in shared folders — add a safe.directory entry, do not disable the check globally

safety checklist  # before any destructive command
1. git status — know what is modified, staged and untracked
2. git branch backup-2026-11-08 — a free safety net before a rebase or reset
3. git log --oneline -5 — confirm you are where you think you are
4. git stash push -u -m "before rebase" — park anything uncommitted
5. Prefer --force-with-lease over --force; prefer revert over reset on public branches
6. When lost: git reflog shows every previous HEAD position, usually for 30–90 days
There is no server-side undo for a force-push. If the remote is the only copy, back it up before rewriting
