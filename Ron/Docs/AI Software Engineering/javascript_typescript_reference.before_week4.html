🌐 Why JavaScript & Where It Runs

JavaScript = "the language of the web"  # every browser runs it natively
Browsers on every device (Windows, Mac, Linux, phones, tablets, TVs) all run JS — users install nothing
Powers the "live" part of pages: clicks, animations, live updates, form checks
Popularity: Python is #1 overall (took the lead ~2019–2020); JavaScript is #2 and still dominates the web
Write once, run anywhere — vs C, which needs porting to every platform
Browser JS vs Server JS  # the key difference is WHERE the code runs
Browser: sent with the HTML/CSS, runs on the user's device — "in the page, reacting to you" (button colour, cart count, slide-out panels)
Server: runs on a remote machine in the cloud, like Python on a backend — receives requests, decides what data/HTML to send back (saved cart, charging a card)
"Modern JavaScript"  # today's standards, tools, and style (not 1999 JS)
Newer language features, current best practices, current tools/build setups
Avoids old clunky patterns, outdated browser hacks, and tangled pre-improvement code
Result: cleaner, safer, more efficient code that fits how the web works now
Course arc: Python → JS → data & logic → async → TypeScript

📤 console.log & Statements

console.log(value);  # JavaScript's print()
Python print("Hello") → JS console.log("Hello");
Multiple args are separated by spaces, like print: console.log("Playlist now:", playlist)
Mindset: same programming logic, different "accent" — mostly syntax changes, not ideas
console.log("Hello, JavaScript!");
console.log("Line 1");   // runs top to bottom
console.log("Line 2");
; semicolon  # ends a statement, same as in C
A statement is a single instruction; ; marks its end like a period
Mostly optional (the engine inserts them automatically), but the course and many style guides say always include them for consistency and to avoid rare edge cases
Code executes top to bottom
// comment   /* block comment */  # Python's # becomes // 
// single-line comment
let x = 5;   // trailing comment
/* multi-line
   comment */
extraTrading-bot style logging  # my example: Python print habits in JS
Same habits you use in the bot, translated
const symbol = "AAPL";
const price = 187.42;
console.log("Symbol:", symbol, "Price:", price);   // like print("Symbol:", symbol, ...)
console.log(`${symbol} @ ${price}`);               // like print(f"{symbol} @ {price}")
console.error("Order rejected");                   // goes to the error stream
console.table([{ s: "AAPL", p: 187.42 }, { s: "JPM", p: 201.1 }]);  // table view in browser devtools

📦 Variables: const & let

const name = value;  # cannot be reassigned — the DEFAULT choice
Python age = 42 → JS const age = 42; (a keyword is required in front)
Use for values that never change: birth year, home city, account creation date
Reassigning throws TypeError: Assignment to constant variable.
const birthYear = 1990;
birthYear = 2000;   // TypeError: Assignment to constant variable.
let name = value;  # can be reassigned (counters, scores, steps)
Use when you know the value will change
Reassign later WITHOUT the keyword: count = 2;
let count = 1;
count = 2;              // fine
let steps = 3;
steps = steps - 1;      // 2
console.log(steps);
Rule: const by default, let only when you plan to reassign
count = 1;  (no keyword)  # must declare before assigning
Python lets you just write count = 1; JS requires let or const first
Using an undeclared name gives ReferenceError: count is not defined
Typo trap from class: count - 1; (minus) instead of count = 1; also gives "count is not defined" — the subtraction reads an undeclared variable
camelCase naming  # JS style; Python uses snake_case
Python favorite_color → JS favoriteColor; home_city → homeCity
Second and later words are capitalized; no underscores
Names are case-sensitive: "fail" vs "Fail" are different strings
extraconst + let in a realistic mini-script  # my example: position tracking 
const maxRisk = 0.02;        // never changes -> const
const symbol = "NVDA";       // never changes -> const
let shares = 0;              // changes as we buy -> let
let avgPrice = 0;

shares = shares + 10;        // or: shares += 10;
avgPrice = 120.5;
shares += 5;                 // compound assignment, same as Python
shares++;                    // increment by 1 (Python has no ++; use += 1)
console.log(shares);         // 16
+= -= *= /= all work as in Python; ++ / -- are JS/C extras

🧬 Basic Types & typeof

string   number   boolean  # the three primitives from Week 1
Python str → JS string  |  Python int + float → JS one type: number  |  Python bool → JS boolean
5 and 5.5 are the SAME type — there is no int/float split
Booleans are lowercase: true / false (Python: True / False)
let myName = "Ron";        // string
let myAge = 59;            // number
let likesCoding = true;    // boolean
typeof value  # JS's version of Python's type()
Returns the type as a lowercase string
console.log(typeof 5);       // "number"
console.log(typeof 5.5);     // "number"
console.log(typeof "hi");    // "string"
console.log(typeof true);    // "boolean"
"5" + 1  →  "51"  # JS converts instead of erroring
Python: "5" + 1 raises TypeError
JS: if one side is a string, + means "glue as text" — the number becomes a string
let result = "5" + 1;
console.log(result);          // 51
console.log(typeof result);   // "string"
No error = silent bug. Be deliberate about string vs number before using +
extraNumber gotchas to know early  # my example: floating point and NaN 
console.log(0.1 + 0.2);          // 0.30000000000000004 (same float issue as Python)
console.log(10 / 3);              // 3.3333333333333335 (no // floor division operator)
console.log(Math.floor(10 / 3));  // 3   (JS replacement for Python //)
console.log(10 % 3);              // 1   (modulo works like Python)
console.log(2 ** 8);              // 256 (same ** power operator)
console.log(Number("42"));        // 42   (like int("42"))
console.log(Number("abc"));       // NaN  (Python would raise ValueError)
console.log(typeof NaN);          // "number" (odd but true)
console.log(typeof null);         // "object" (famous historical bug)
No floor-division operator in JS: use Math.floor(a / b)

🔀 Conditions & Curly Braces

if (cond) { } else if (cond) { } else { }  # parentheses + braces
Condition goes in parentheses; the block goes in curly braces instead of indentation
Python elif → JS else if; no colon
Indentation is only for humans in JS — the {} define the block
let score = 85;
if (score >= 90) {
  console.log("A");
} else if (score >= 80) {
  console.log("B");
} else {
  console.log("Keep going");
}
{ } curly braces  # mark where a block starts and ends
Group lines in the same local scope — the job Python's indentation does
A let/const declared inside a block is scoped to that block
&&   ||   !  # and / or / not
Python and → &&
Python or → ||
Python not → !
let temperature = 72;
if (temperature >= 68 && temperature <= 75) {
  console.log("Comfortable");
} else {
  console.log("Not comfortable");
}

let day = "Saturday";
if (day === "Saturday" || day === "Sunday") {
  console.log("Weekend");
}
Repeat the full comparison on both sides: day === "Sat" || day === "Sun", not day === "Sat" || "Sun"
extraTernary operator (one-line if/else)  # my example: compact conditional
Python "Pass" if score >= 70 else "Fail" → JS score >= 70 ? "Pass" : "Fail"
const score = 80;
const result = score >= 70 ? "Pass" : "Fail";
console.log(result);   // Pass

📝 Template Literals (JS f-strings)

`Hello, ${name}`  # backticks + ${} = Python's f"Hello, {name}"
Python f"Hi {name}" → JS `Hi ${name}` — backticks (key above Tab), no f prefix
Anything inside ${ } is evaluated: variables and expressions
const name = "Ron";
const age = 59;
const info = `Name: ${name}, Age: ${age}`;
const next = `Next year, ${name} will be ${age + 1} years old.`;
console.log(info);
console.log(next);
Normal quotes do NOT interpolate: "Hello ${name}" prints the literal text Hello ${name} (like leaving off the f in Python)
multi-line strings  # just press Enter inside the backticks — no \n, no +
Python equivalent: triple-quoted f-string
Line breaks in the code become line breaks in the string
const profile = `Profile for ${name}
Name: ${name}
Age: ${age}`;
console.log(profile);

// old way (avoid):
const old = "Profile for Ron\n" + "Name: Ron\n" + "Age: 59";
extraFormatting numbers inside templates  # my example: like f"{x:.2f}"
Python f"{price:.2f}" → JS ${price.toFixed(2)} (returns a string)
const price = 187.4;
console.log(`Price: $${price.toFixed(2)}`);   // Price: $187.40
console.log(`Total: ${(price * 3).toFixed(2)}`);
console.log(`Sum: ${1 + 2}`);                 // expressions allowed
Write a literal dollar sign before ${} as $${...}

⚖️ Equality & Missing Values

===   !==   (strict)  vs  ==   !=   (loose)  # ALWAYS use ===
== loose: converts types first → "5" == 5 is true
=== strict: compares value AND type, no conversion → "5" === 5 is false
Three different symbols: = assigns, === compares
console.log("5" == 5);    // true
console.log("5" === 5);   // false
console.log(0 == "0");    // true  (avoid)
console.log(0 === "0");   // false
Use === and !== in all new code (class correction: a stray day == "Sunday" was flagged)
null   vs   undefined  # two kinds of "no value"
null — deliberately empty: "I know about this value and it is empty now" (closest to Python's None). Examples: no nickname, "no selection" in a dropdown
undefined — nothing assigned yet: a declared variable with no value, a field to be filled by input or a file read
let middleName;               // undefined
let nickname = null;          // intentionally empty
console.log("middleName is:", middleName);   // undefined
console.log("nickname is:", nickname);       // null

if (middleName === undefined) { console.log("not set yet"); }
if (nickname === null) { console.log("no nickname, on purpose"); }
falsy  vs  truthy  # what counts as false inside if (...)
Falsy: false, 0, "" (empty string), null, undefined, NaN
Truthy: everything else — e.g. any non-empty string like "hello"
if (false)   { console.log("no"); }
if (0)       { console.log("no"); }
if ("")      { console.log("no"); }
if ("hello") { console.log("runs!"); }   // only this one prints

let userName = "";
if (userName === "") { console.log("username is empty"); }
if (!userName)       { console.log("also empty (falsy check)"); }
Extra (not from class notes): unlike Python, empty arrays [] and empty objects {} are TRUTHY in JS
extraSafe "is it missing?" checks  # my example: null/undefined helpers 
let value;                          // undefined
console.log(value === undefined);   // true
console.log(value === null);        // false  (strict says they differ)
console.log(value == null);         // true   (the one common exception: matches null OR undefined)
console.log(value ?? "default");    // "default" (nullish coalescing: fallback only for null/undefined)
console.log(0 || "fallback");       // "fallback" (|| also replaces 0 and "")
console.log(0 ?? "fallback");       // 0 (?? keeps 0, "" and false)
?? is usually the safer default-value operator than ||

📚 Arrays (JS Lists)

let colors = ["red", "green", "blue"];  # Python list → JS array
Square brackets, commas, ordered — looks the same as a Python list
Zero-based indexing: colors[0] is "red"
let playlist = ["Intro", "Verse", "Chorus"];
console.log(playlist[0]);   // Intro
console.log(playlist[2]);   // Chorus
array.length  # property, NOT a function — Python's len(list)
fruits.length → number of items (no parentheses!)
Last valid index is length - 1
let fruits = ["apple", "banana", "cherry", "date"];
console.log(fruits.length);                 // 4
console.log(fruits[fruits.length - 1]);     // "date"  (last item)
fruits.length - 1 is the last INDEX (3); you still need fruits[...] around it to get the item
Negative indexes like Python's list[-1] do NOT work this way in JS — use length - 1
array.push(item)  # add to the END — Python's list.append()
Changes the array in place, so .length grows too
let playlist = ["Intro", "Verse"];
playlist.push("Chorus");
console.log(playlist);          // [ 'Intro', 'Verse', 'Chorus' ]
console.log(playlist.length);   // 3
array.pop()  # remove AND return the last item — same name as Python 
let playlist = ["Intro", "Verse", "Chorus"];
let lastTrack = playlist.pop();
console.log("Playlist now:", playlist);       // [ 'Intro', 'Verse' ]
console.log("Last track was:", lastTrack);    // Chorus
console.log("Length now:", playlist.length);  // 2
extraMore array operations to preview  # my example: a few beyond Week 1 
const prices = [10, 20, 30];
prices.unshift(5);            // add to FRONT      -> [5, 10, 20, 30]
const first = prices.shift(); // remove FROM FRONT -> first = 5
console.log(prices.includes(20));       // true  (Python: 20 in prices)
console.log(prices.indexOf(30));        // 2     (-1 if not found)
console.log(prices.slice(0, 2));        // [10, 20] (like prices[0:2])
console.log(prices.join(" | "));        // "10 | 20 | 30"
for (const p of prices) {               // like: for p in prices:
  console.log(p);
}
push/pop/shift/unshift CHANGE the array; const only blocks reassigning the variable, not changing its contents

🗃️ Objects (JS Dicts)

const person = { name: "Ron", age: 59 };  # Python dict → JS object
Curly braces, key: value pairs, commas between. Keys are normally written without quotes (Python dict keys are quoted strings)
Read with dot notation: person.name (Python: person["name"])
const person = { name: "Ron", age: 59, likesCoding: true };
console.log(person.name);    // "Ron"
console.log(person.age);     // 59
console.log(person.email);   // undefined  (missing key = undefined, NOT an error like Python's KeyError)
person["name"]  vs  person[key]  # bracket notation = dynamic keys
Dot needs the literal key name. Brackets accept any expression — use them when the key is in a variable or has spaces
const key = "age";
console.log(person[key]);        // 59   (variable holds the key name)
console.log(person.key);         // undefined (looks for a key literally named "key")
person["favorite color"] = "blue";   // awkward key name needs brackets
person.key is NOT the same as person[key] — the classic dynamic-key mistake
add / change / delete properties  # objects are mutable, even when declared const 
const car = { make: "Ford" };
car.year = 2020;        // add
car.make = "Toyota";    // change
delete car.year;        // remove  (Python: del car["year"])
console.log(car);       // { make: 'Toyota' }
const only stops re-pointing the variable; the contents can still change (same as arrays)
Check a key exists: "make" in car → true (Python: "make" in car)
Methods & nested objects  # functions and objects inside objects 
const account = {
  owner: "Ron",
  address: { city: "Tampa", zip: "33601" },   // nested object
  tags: ["trader", "student"],                // array inside
  greet: function () { console.log("Hi " + this.owner); }   // method
};
console.log(account.address.city);   // "Tampa"
console.log(account.tags[0]);        // "trader"
account.greet();                     // Hi Ron
Handy lookups: Object.keys(obj), Object.values(obj), Object.entries(obj) (Python: .keys() .values() .items())

🔁 Loops: while, for, for...of

while (condition) { }  # repeat while true — same idea as Python while
Parentheses around the condition, braces around the body. Make sure something inside changes the condition or it never ends
let count = 3;
while (count > 0) {
  console.log(count);
  count--;              // without this: infinite loop
}
console.log("Liftoff");
break exits the loop; continue skips to the next pass (same as Python)
for (let i = 0; i < n; i++) { }  # classic for: start; keep-going test; step
Three parts in the parentheses, separated by ;: init (let i = 0), condition (i < n), update (i++)
Python for i in range(5): → JS for (let i = 0; i < 5; i++)
for (let i = 0; i < 5; i++) {
  console.log(i);              // 0 1 2 3 4
}

const fruits = ["apple", "banana", "cherry"];
for (let i = 0; i < fruits.length; i++) {
  console.log(i, fruits[i]);   // index AND item (Python: enumerate)
}
Count down: for (let i = 10; i > 0; i--)  |  step by 2: i += 2
for (const item of array) { }  # Python's for item in list: — use this to loop over values 
for (const fruit of fruits) {
  console.log(fruit);          // apple, banana, cherry
}
for (const ch of "hey") { console.log(ch); }   // works on strings too
Use const here: a fresh variable is made each pass
for...in  vs  for...of  # the gotcha: Python's "in" is JS's "of"
for...of gives the VALUES (what Python's for x in list does)
for...in gives the KEYS — array indexes (as strings!) or object property names
const colors = ["red", "green"];
for (const c of colors) console.log(c);   // red, green
for (const i in colors) console.log(i);   // "0", "1"   (indexes, not items!)

const person = { name: "Ron", age: 59 };
for (const key in person) {
  console.log(key, person[key]);          // name Ron / age 59  (Python: for k in d)
}
// for (const x of person) -> TypeError: person is not iterable  (plain objects can't use of)
Rule of thumb: arrays → of; objects → in (or Object.entries). Writing in on an array gives indexes, not items
extraLooping over an object with entries  # my example: closest to Python's .items() 
const prices = { AAPL: 187.4, JPM: 201.1 };
for (const [symbol, price] of Object.entries(prices)) {   // destructuring in the loop
  console.log(`${symbol}: ${price}`);
}

📥 Destructuring & Spread

const [a, b] = array;  # array destructuring — unpack BY POSITION
Python tuple unpacking: a, b = [1, 2] → JS const [a, b] = [1, 2];
const colors = ["red", "green", "blue"];
const [first, second] = colors;       // first="red", second="green"
const [, , third] = colors;           // skip with empty slots -> "blue"
const [x, y, z, w] = colors;          // w is undefined (not enough items)
let p = 1, q = 2;
[p, q] = [q, p];                      // swap (Python: p, q = q, p)
Names are yours to choose — position decides what goes where
const { name, age } = object;  # object destructuring — unpack BY NAME
Variable names must match the property names; order doesn't matter
const person = { name: "Ron", age: 59, city: "Tampa" };
const { name, age } = person;               // name="Ron", age=59
const { city: homeCity } = person;          // rename: homeCity = "Tampa"
const { email } = person;                   // undefined (missing key)
const { zip = "00000" } = person;           // default if undefined
Also works in function parameters: function show({ name, age }) { ... }
Array = by position ([ ]), object = by name ({ }). Mixing the brackets up is the usual slip
Mutability & reference aliasing  # two names, ONE object
Arrays and objects are references: assigning copies the pointer, not the data (same as Python lists/dicts)
const a = { score: 1 };
const b = a;            // b points at the SAME object
b.score = 99;
console.log(a.score);   // 99  -- a changed too!

console.log({ x: 1 } === { x: 1 });   // false: different objects, even if equal contents
Strings, numbers, booleans are copied by value — changing one never affects the other
...spread   (copy & merge)  # three dots spread items out
Python [*a, *b] / {**a, **b} → JS [...a, ...b] / {...a, ...b}
const nums = [1, 2, 3];
const copy = [...nums];             // new array, independent
const more = [...nums, 4, 5];       // [1,2,3,4,5]

const base = { name: "Ron", age: 59 };
const updated = { ...base, age: 60 };    // copy + override -> { name:'Ron', age:60 }
const merged = { ...base, city: "Tampa" };
Spread is a shallow copy: nested arrays/objects inside are still shared with the original
Later keys win when names collide, so put overrides last

🔧 Functions

function name(params) { return value; }  # Python's def
Python def add(a, b): → JS function add(a, b) { } — braces, no colon, camelCase names
Define it, then call it with (). No return = the call gives undefined (Python: None)
function add(a, b) {
  return a + b;
}
const total = add(2, 3);
console.log(total);        // 5

function sayHi(name) { console.log("Hi " + name); }   // no return
console.log(sayHi("Ron"));  // prints Hi Ron, then undefined
Default params & multiple return values  # same ideas, different shapes 
function greet(name = "friend") {      // default (same as Python)
  return `Hello, ${name}`;
}
greet();            // "Hello, friend"
greet("Ron");       // "Hello, Ron"

function minMax(arr) {
  return [Math.min(...arr), Math.max(...arr)];   // return an array (or object)
}
const [lo, hi] = minMax([4, 9, 2]);              // destructure the result
JS can only return ONE thing — wrap several in an array (by position) or object (by name). Extra arguments are ignored; missing ones are undefined
Code after a return never runs
extraFunctions + loops challenge pattern  # my example: loop inside a function, return the result 
function sumArray(numbers) {
  let total = 0;
  for (const n of numbers) {
    total += n;
  }
  return total;               // return AFTER the loop, not inside it
}
console.log(sumArray([1, 2, 3, 4]));   // 10

function coinFlip() {
  return Math.random() < 0.5 ? "Heads" : "Tails";
}
Class coin-flip slip: Math.floor(Math.random() * 4) - 2 gives -2..1, so "result === 1" is only 1-in-4. Use Math.floor(Math.random() * 2) for 0 or 1
return inside the loop body ends the function on the FIRST pass

🧩 Functions as Values, Callbacks & Anonymous Functions

const greet = function sayHello(name) { };  # function expression: a function stored in a variable
Python: say_hello = greet — functions are values you can put in variables. JS does the same
The variable is the "box"; () uses the tool inside it
const action = function doSomething() {
  console.log("Doing something...");
};
action();      // calls it
action;        // just the function itself (not run)
greet = the function (a value)  |  greet() = CALL it now. Missing or extra () is the #1 mix-up
Callbacks: passing a function in  # "first-class functions"
A function can be an argument. The one passed in is a callback; the receiver decides when to call it
function greet() { console.log("Hello from greet"); }

function runTask(task) {
  console.log("About to run the task...");
  task();                          // call the function we were given
  console.log("Finished.");
}
runTask(greet);       // pass the function itself: NO parentheses
// runTask(greet());  // WRONG: calls greet now, passes its result (undefined)
Why "functions are values": store them in variables, pass them to functions, call them later
function() { ... }  (no name)  # anonymous function: just drop the name 
let greet = function greetFunction() { console.log("Hi"); };  // named expression
let greet2 = function () { console.log("Hi"); };              // anonymous: same behaviour

let sayOnce = function () { console.log("Runs when called"); };
sayOnce();
Recognise the shape function () { ... } sitting inside another call — that is an anonymous callback
setTimeout(function () { }, ms)  # run a callback LATER 
setTimeout(function () {
  console.log("This runs after 2 seconds");
}, 2000);
console.log("This prints first");   // program keeps going; timer fires later
The callback does NOT run immediately: JS stores it, finishes the current code, then calls it after the delay (ms: 1000 = 1 second)
Async preview: the program "finishes", then the timer's output appears (full coverage in the Week 3 sync/async section)
(params) => { }  # arrow function: shorter anonymous function
Drop the word function, add => after the parameters. Similar to Python's lambda, but can hold full code blocks
One expression and no braces = implicit return (the value is returned automatically)
const add = function (a, b) { return a + b; };   // old way
const add2 = (a, b) => { return a + b; };          // arrow, braces: needs return
const add3 = (a, b) => a + b;                      // arrow, implicit return

const double = n => n * 2;                         // one param: () optional
const hello = () => console.log("Hi");             // no params: () required

setTimeout(() => console.log("after 1s"), 1000);   // arrow as callback
[1, 2, 3].forEach(n => console.log(n));
With braces { } you MUST write return; without braces the value returns itself. Returning an object literal: wrap in parens () => ({ a: 1 })

🔁 forEach() — Run a Function on Every Item

arr.forEach(function (item, index) { })  # do something for each element, in order
Python: for color in colors: print(color) — JS lets the array call YOUR function once per item (a callback)
1st parameter = the value (name is your choice: food, item…). 2nd parameter = the index, starting at 0
const foods = ["scallops", "steak", "crabs"];

foods.forEach(function (food, index) {
  console.log(index, food);
});
// 0 scallops
// 1 steak
// 2 crabs
Python equivalent of the index version: for index, food in enumerate(foods)
forEach returns undefined  # it's for side effects, not for building a new array 
const result = foods.forEach(function (food) { console.log(food); });
console.log(result);          // undefined
Side effect = logging, or updating a variable that lives OUTSIDE the callback (accumulator pattern)
const scores = [5, 15, 20, 30];
let total = 0;                       // lives outside the callback
scores.forEach((score, index) => {   // arrow-function callback
  total = total + score;             // 0 -> 5 -> 20 -> 40 -> 70
});
console.log("Total is:", total);     // Total is: 70
Python: total = 0; for score in scores: total = total + score
Want a NEW array back? forEach is the wrong tool — use map() or filter() (next section)

🔁 map() & filter()

const newArr = oldArr.map(callback)  # transform EVERY item → same-length new array
Python: [n * 3 for n in nums] (list comprehension)
Callback's return value = what goes into the new array at that position
const myArray = [1, 2, 3];
function tripleIt(num) { return num * 3; }

const mappedArray = myArray.map(tripleIt);   // pass the function: NO parentheses
console.log(myArray);       // [1, 2, 3]   original untouched
console.log(mappedArray);   // [3, 6, 9]

const percentages = [60, 80, 90].map(n => n / 100);   // [0.6, 0.8, 0.9]
Use when: one input → one output (add tax to each price, turn scores into percentages)
const newArr = oldArr.filter(callback)  # KEEP only items where the callback is true
Python: [n for n in nums if n % 2 == 0]
Callback returns true/false: true = keep the original item, false = drop it. Result may be shorter
const numbers = [1, 3, 4, 5, 6, 8, 9];
function isEven(n) { return n % 2 === 0; }

const even = numbers.filter(isEven);
console.log(numbers);   // [1, 3, 4, 5, 6, 8, 9]   original untouched
console.log(even);      // [4, 6, 8]

const high = [60, 70, 80, 85, 90].filter(n => n >= 80);   // [80, 85, 90]
The test can be anything: evens, holidays, rainy days, scores above 90…
map vs filter  (can't map do a filter?)  # no: map stores the return value, filter uses it as keep/drop 
const nums = [1, 2, 3, 4];
const mapped   = nums.map(n => n % 2 === 0);      // [false, true, false, true]  (booleans, same length)
const filtered = nums.filter(n => n % 2 === 0);   // [2, 4]                      (original numbers kept)
map()filter()
"What is the NEW value for this item?""Keep this ORIGINAL item?"
Always same length as the originalSame length or shorter
Returns a new arrayReturns a new array
Original array never changedOriginal array never changed
Chaining: arr.filter(...).map(...)  # first select, then transform 
const scores = [60, 70, 80, 85, 90];

const result = scores
  .filter(score => score >= 80)   // 1. keep high scores -> [80, 85, 90]
  .map(score => score / 100);     // 2. to 0-1 percentages -> [0.8, 0.85, 0.9]

console.log(result);   // [0.8, 0.85, 0.9]   scores is still [60, 70, 80, 85, 90]
Each step returns a new array, so the next method can be chained straight onto it
Arrow function + map: braces need return  # the classic [undefined, undefined, undefined] bug 
const nums = [1, 2, 3];
const a = nums.map(n => n * 2);                 // [2, 4, 6]  implicit return (no braces)
const b = nums.map(n => { n * 2 });             // [undefined, undefined, undefined]  BROKEN
const c = nums.map(n => { return n * 2; });     // [2, 4, 6]  fixed
Braces { } = you must write return. No braces = the expression is returned for you

🌐 APIs, Client & Server (Why Async Exists)

API = the messenger between two systems  # you follow its rules, you don't need its internals
Takes a request from one system, delivers it to another, brings back a response in a format the first one understands
Client = the side that asks (browser page / app code near the user). Server = the remote machine that has the data and answers
Why use APIs: reuse another system's data or features (weather, exchange rates, maps) instead of rebuilding them
Client  --request-->  Server
Client  <--response--  Server   (client then updates the screen)
Why a request takes time  # the "waiting problem"
Total delay = request travel + server working + response travel
If the program froze while waiting, the page would lock up (no scrolling, typing, clicking) and users would get annoyed and leave
Python: requests.get(url) normally BLOCKS until the data is back. JS does not wait — that is the whole point of async

⏱️ Synchronous vs Asynchronous & the Event Loop

Synchronous: one line at a time, in order  # each line finishes before the next starts 
console.log("A");
console.log("B");
console.log("C");   // always A, B, C
Asynchronous: start it now, finish it later  # setTimeout(callback, ms) does NOT pause the code 
console.log("Start");
setTimeout(function () {
  console.log("Done");
}, 1000);
console.log("End");
// Start
// End
// (about 1 second later) Done
setTimeout schedules the callback "at least this many ms from now" and JS keeps running the next lines
First argument must be a function REFERENCE: setTimeout(myFunction, 1000). setTimeout(myFunction(), 1000) runs it immediately and passes its result
Event loop: "main line" and "waiting area"  # simple mental model
Main line: normal code, top to bottom. Waiting area: delayed tasks (timers, network) sit there until ready
Event loop asks: "Is the main line free? Is any waiting task finished? If yes, run its callback now"
All synchronous lines run FIRST, even with a delay of 0; callbacks run only when the main line is free
console.log("One");
setTimeout(function () { console.log("Two"); }, 1000);
console.log("Three");
setTimeout(function () { console.log("Four"); }, 500);
console.log("Five");
// One, Three, Five   (sync first)
// Four               (500 ms timer finishes first)
// Two                (1000 ms timer finishes last)
console.log("First");
setTimeout(function () { console.log("Second"); }, 0);
console.log("Third");
// First, Third, Second   (even 0 ms waits for the main line)

📡 fetch() & Promises

fetch(url)  # starts a request; returns a Promise right away 
fetch("https://jsonplaceholder.typicode.com/posts/1");   // runs silently, no output

const result = fetch("https://jsonplaceholder.typicode.com/posts/1");
console.log(result);   // Promise {}  (not the data!)
Promise {} is not "empty" or "broken": it is the placeholder object for a result that is not ready yet. The console can't show what's inside
My analogy: the ticket you get at the dry cleaners — you use it later to pick up the right jacket
Promise states: pending / fulfilled / rejected  # settled = fulfilled or rejected
StateMeaningRide-app picture
pendingstill in progress, result not readydriver is on the way / searching
fulfilledfinished successfullypicked up and arrived
rejectedfinished with a failure"No drivers available"
settledno longer pending (fulfilled OR rejected)the story is over either way
A Promise is a sealed envelope holding a future result: you can't open it while pending
const promise = fetch("https://httpbin.org/delay/3");   // answers after ~3 seconds
console.log(promise);   // Promise {}  <- still pending, you only have the envelope
promise.then(callback)  # run this when the Promise is FULFILLED 
console.log("A: starting");
const result = fetch("https://jsonplaceholder.typicode.com/posts/1");
result.then(() => {
  console.log("C: request finished");
});
console.log("B: ending sync code");
// A: starting
// B: ending sync code
// C: request finished     (.then callback is always LATER than the sync lines)
Usual style: chain it straight on the call — fetch(url).then((response) => { ... });
The real response only exists inside the .then callback, not on the line after fetch()
.catch(callback)  # run this when the Promise is REJECTED
.then() = success handler, .catch() = failure handler (Python: except)
console.log("1: before bad fetch");
fetch("https://this-domain-should-not-exist-12345.com")
  .then(() => { console.log("2: this will NOT run on failure"); })
  .catch(() => { console.log("3: fetch failed"); });
console.log("4: after bad fetch call");
// 1, 4, then 3 later
An error thrown INSIDE a .then() also rejects the chain, so the next .catch() runs:
console.log("A: start");
fetch("https://jsonplaceholder.typicode.com/posts/1")
  .then(() => {
    console.log("B: inside then before error");
    throw new Error("Boom from then");
  })
  .catch(() => { console.log("C: inside catch after error"); });
console.log("D: end of script");
// order: A, D, B, C
Response → response.json() → data  # two .then() steps to get usable data
The first .then() gets a Response object (the box), NOT the data inside it
JSON = text that looks like a JS object. response.json() turns it into a real object, and it returns another Promise
fetch("https://jsonplaceholder.typicode.com/posts/1")
  .then((response) => {
    return response.json();            // Promise of the parsed data
  })
  .then((data) => {
    console.log("Post title:", data.title);   // data is a normal JS object
  })
  .catch((error) => {
    console.error("Error:", error);
  });
Flow: fetch → Response → response.json() → data object
Forgetting return before response.json() means the next .then gets undefined

✨ async / await

async function name() { }  # allows await inside; always returns a Promise
async alone does not delay anything — the function body still runs top to bottom until it reaches an await
async function loadPosts() {
  console.log("loadPosts started");
}
console.log("Before calling loadPosts");
loadPosts();
console.log("After calling loadPosts");
// Before calling loadPosts
// loadPosts started
// After calling loadPosts
const x = await somePromise;  # pause THIS function until the Promise settles
Without await: x is the raw Promise (Promise {}). With await: x is the real value
async function loadPosts() {
  console.log("loadPosts started");
  const response = await fetch("https://jsonplaceholder.typicode.com/posts/1");
  const data = await response.json();
  console.log("Data inside loadPosts:", data);
}
console.log("Before calling loadPosts");
loadPosts();
console.log("After calling loadPosts");
// Before calling loadPosts
// loadPosts started
// After calling loadPosts          <- runs BEFORE the data line
// Data inside loadPosts: { userId: 1, id: 1, title: "...", body: "..." }
Only the async function pauses at await; the rest of the program keeps running (non-blocking)
await only works inside an async function
.then() chain vs async/await  # same logic, two styles 
// then-style: compact, but logic is split across callbacks
fetch(url)
  .then(response => response.json())
  .then(data => console.log(data))
  .catch(error => console.error(error));

// async/await style: reads top to bottom like normal code
async function loadPosts() {
  try {
    const response = await fetch(url);
    const data = await response.json();
    console.log(data);
  } catch (error) {
    console.error(error);
  }
}
As steps and error handling grow, async/await is easier to read. Python parallel: try / except ↔ try / catch

🔗 Dependent Requests & Error Handling

Request 2 needs data from request 1  # must await the first before building the second URL 
async function loadPosts() {
  try {
    const response = await fetch("https://jsonplaceholder.typicode.com/posts/1");
    const data = await response.json();
    console.log(data);

    const userId = data.userId;                                          // only known AFTER the await
    const userUrl = `https://jsonplaceholder.typicode.com/users/${userId}`;

    const userResponse = await fetch(userUrl);
    const userData = await userResponse.json();
    console.log("User Object:", userData);
  } catch (error) {
    console.error("Something went wrong:", error);   // ONE place for any step's failure
  }
}
loadPosts();
Dependent = sequential: you can't build /users/${userId} until the first response gives you userId
One try / catch around the whole flow: if step 1 fails, the user fetch is skipped and you get one clear error
Independent requests (you already know the ids) don't depend on each other, so they could be started together (e.g. Promise.all, covered only as a teaser)
Forget await on response.json() and data is a Promise, so data.userId is undefined
