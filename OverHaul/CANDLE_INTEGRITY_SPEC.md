# CANDLE INTEGRITY SPEC — Phase 2
**Date:** 2026-05-10  
**Status:** Implemented  
**File changed:** `scanners/market_scanner.py`

---

## Contract

> **No strategy may evaluate a bar whose expected close time is still in the future.**

This is the closed-candle contract. It applies to every signal generated by the scanner for both stocks and crypto. It does not apply to the backtester (which uses yfinance historical data — all bars are already closed).

---

## Problem Being Fixed

### Root cause (ISSUE-05 from PARITY_AUDIT.md)

Both `StockScanner.get_bars()` and `CryptoScanner.get_ohlcv()` previously returned the currently-forming bar as the last element of the DataFrame:

- **Kraken CCXT** (`fetch_ohlcv`): always includes the bar currently in progress
- **Alpaca** (`get_bars`): includes the bar currently accumulating

Strategies received this bar and computed indicators against its close, high, and low — values that are still changing intrabar.

**Concrete impact:** A 1h crypto strategy using a 5-minute scan cycle would receive 12 different versions of the same forming hourly candle before it closed, each with different indicator readings. Any signal generated during this window was based on provisional data that would change before the bar closed.

### Secondary problem (re-evaluation of same closed bar)

Even after fixing the forming-bar issue, a 5-minute scanner hitting a 1h strategy would still re-evaluate the same closed bar 12 times per hour (once per scan cycle). The bar is closed and stable, so the indicator result would be identical — but strategy code was being re-run needlessly, and in theory the same signal could re-fire if the position had been closed by other logic between scan cycles.

## Implementation

### New utility functions (market_scanner.py)

#### `_tf_to_seconds(timeframe: str) -> int`
Converts a timeframe string (CCXT or Alpaca format) to its duration in seconds.

Supported formats:
| Input | Seconds |
|---|---|
| `"1m"`, `"1min"`, `"1minute"` | 60 |
| `"5m"`, `"5min"`, `"5Min"` | 300 |
| `"15m"`, `"15min"`, `"15Min"` | 900 |
| `"30m"`, `"30min"` | 1800 |
| `"1h"`, `"1hour"`, `"1Hour"`, `"60m"`, `"60min"` | 3600 |
| `"2h"`, `"2hour"` | 7200 |
| `"4h"`, `"4hour"` | 14400 |
| `"1d"`, `"1day"`, `"daily"` | 86400 |

Falls back to 300 (5 minutes) if unrecognised — conservative, strips by default.

#### `_strip_forming_bar(df, timeframe) -> DataFrame`
Checks the last bar in `df`. If `now_utc < bar_start + timeframe_seconds`, the bar is still forming and is removed from the DataFrame. Otherwise returns `df` unchanged.

Timezone handling:
- Kraken CCXT bars: naive UTC (from ms-epoch conversion) — compared directly against `datetime.utcnow()`
- Alpaca bars: may be tz-aware UTC — normalised to naive UTC via `tz_convert("UTC").tz_localize(None)` before comparison

If the timestamp cannot be parsed, the bar is kept unchanged (fail-open, conservative).

### Changes to `StockScanner.get_bars()`
- Now requests `limit + 1` bars from Alpaca (one extra to compensate for stripping)
- Calls `_strip_forming_bar(bars, timeframe)` before returning
- Returns `None` if the result is empty after stripping

### Changes to `CryptoScanner.get_ohlcv()`
- Now requests `limit + 1` bars from Kraken (one extra to compensate for stripping)
- Calls `_strip_forming_bar(df, timeframe)` before returning
- Returns `None` if the result is empty after stripping

### New instance variable: `_last_bar_evaluated`
Added to both `StockScanner` and `CryptoScanner`.

```python
self._last_bar_evaluated: Dict[str, str] = {}
# Key:   "{SYMBOL}_{TIMEFRAME}"   e.g. "BTC/USD_1h"
# Value: str(bars.index[-1])      last closed bar timestamp
```

In each `scan()` method, after fetching bars for a symbol+timeframe, the scanner checks whether the last closed bar timestamp has changed from the previous scan cycle. If unchanged, the timeframe is skipped entirely for signal generation (same bar, same result). If changed (new bar has closed), the cache is updated and strategies run.

## Behaviour After This Change

### Before
```
BTC/USD  1h strategy  scan at 10:00  → evaluates forming 1h bar (started 10:00, closes 11:00)
BTC/USD  1h strategy  scan at 10:05  → evaluates SAME forming bar, different close price
BTC/USD  1h strategy  scan at 10:10  → evaluates SAME forming bar, different close price
... (12 times total before 11:00)
BTC/USD  1h strategy  scan at 11:00  → evaluates forming 11:00 bar (next one, still forming)
```

### After
```
BTC/USD  1h strategy  scan at 10:00  → forming bar stripped; last closed bar is 09:00 bar
                                        09:00 bar not yet evaluated → strategies run once
BTC/USD  1h strategy  scan at 10:05  → forming bar stripped; last closed bar is still 09:00
                                        SAME bar → [CANDLE SKIP] logged, strategies skipped
BTC/USD  1h strategy  scan at 10:10  → same
... (skipped until 11:00)
BTC/USD  1h strategy  scan at 11:00  → forming 11:00 bar stripped; last closed bar is 10:00
                                        NEW bar → strategies run once
```

The same pattern applies to stock 1h strategies with 60-second scan cycles.

## Acceptance Criteria

| Criterion | How to Verify |
|---|---|
| Crypto 1h strategy is not re-evaluated on the same forming bar every 5 minutes | Log shows `[CANDLE SKIP]` for all scan cycles between hourly bar closes |
| Stock 1h strategy is not re-evaluated on forming hourly candles every 60 seconds | Log shows `[CANDLE SKIP]` for all scan cycles between hourly bar closes |
| Forming bar removed from every fetch | Log shows `[CANDLE STRIP]` when a bar has not yet closed |
| Strategies still receive enough bars | `get_bars(limit=100)` returns 100 closed bars (fetches 101, strips 1) |
| Position monitor still works | `_get_bars()` in position_monitor calls the same methods; still receives correct closed bars |

## Scope Boundary — What This Phase Does NOT Fix

- **ISSUE-09/10 (timeframe-aware monitor):** The position monitor still hardcodes 5m bars. This requires `entry_timeframe` to be stored in the trade record — that is Phase 4.
- **ISSUE-06/14 (entry at signal bar close):** The backtester still enters at bar `i` close. That is Phase 5.
- **ISSUE-01 (same-bar two_bar stop):** Stop engine changes are Phase 3.
- **ISSUE-12 (fees/slippage):** Realism hardening is Phase 5.
